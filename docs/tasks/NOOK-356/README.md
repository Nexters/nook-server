# NOOK-356 게시글 관리 중심 처리 상세와 실패 원인

## 목적

실패 목록에서 게시글을 클릭하면 그 게시글만의 처리 상태와 원인으로 바로 이동한다.
목록과 처리 흐름을 한 화면에 쌓지 않고, 게시글 관리에서 실패 분류·재시도·운영 상태 변경을 수행한다.

## 범위와 성공 기준

- 게시글 관리에 최근 실패, 관리자 재시도 실패, 처리 중, 완료, 처리 불가 목록을 둔다.
  실패 목록은 실제 마지막 실패 시각 기준 최근 7일이 기본이고 오늘/30일/전체 기간도 선택한다.
  관리자 재시도 실패는 총 실행 횟수가 현재 재시도 회차의 실행 횟수보다 큰 실패 작업으로 구분한다.
  진행 중인 작업이 있으면 처리 중에 표시하고 종료된 실패 목록에는 중복 노출하지 않는다.
- 목록은 게시글당 한 카드, 페이지당 10개로 요약한다. 상세는 `/posts/:postId/processing`에서
  게시글 제목·번호, 현재 상태, 단계별 완료/실패, 구체적인 원인·오류 코드·실행 횟수를 표시한다.
  목록 복귀 시 분류와 기간은 유지하고 페이지·스크롤은 처음으로 돌아간다.
- 처리 중에는 상태와 실행 이력을 5초마다 갱신한다. 재시도로 완료된 작업은 복구 완료로 구분한다.
- 최신 실행 회차를 기본으로 보여주고 이전 이력은 선택해서 펼친다. 조건 불충족은 실제 오류와
  구분하며 같은 사유로 생략한 조건은 묶는다. 조건의 이름·판정 사유·근거는 펼쳐서 확인한다.
- 별도 파이프라인 메뉴와 대시보드 카드를 없애고 게시글 관리의 처리 규칙 탭으로 통합한다.
  기존 파이프라인 주소는 처리 규칙 탭으로, postId/recoveryPostId 링크는 해당 게시글 상세로 연결한다.
- 처리 불가는 관리자만 사유를 남겨 수동으로 변경한다. 관리자 재시도가 실패해도 자동 전환하지 않는다.
  실패 작업의 상태·시각·횟수는 보존하고 별도 운영 분류로 관리한다. 처리 불가 상태에서는
  게시글 전체/개별 작업 재시도를 모두 차단하며, 복구 대상으로 되돌린 뒤 다시 시도할 수 있다.
  상태 변경과 감사 기록은 하나의 짧은 트랜잭션이다. 작업 잠금 순서는 기존 전체 재시도와 동일하다.
- 게시글 최종 종료 요약 알림의 한 건 발행 정책을 유지한다. 단계·사유별 건수에 오류 코드,
  상세 사유(최대 400자), 최대 실행 횟수, 관리자 재시도 여부, 해당 게시글 상세 링크를 추가한다.
  URL·Bearer 및 비밀 키 값은 가린다. 정상 장소 0개 저장/전체 성공에는 기존대로 알리지 않는다.

## API 및 DB

- 기존 API 계약을 유지하고 복구 응답에 제목·운영 분류·변경 사유/시각과 구조화한 실패 정보를 추가한다.
- `GET /api/admin/v1/post-processing`: category, failedSince, page, limit, postId는 선택 입력이다.
- `PATCH /api/admin/v1/post-processing/{postId}/disposition`: OPEN/UNPROCESSABLE과 필수 사유(최대 500자).
  처리 중, 동일 상태 변경, 실패 없는 게시글의 처리 불가 분류, 처리 불가 게시글 재시도는 409다.
- `ddl/up.sql`은 MySQL 8.4 INSTANT로 posts에 운영 분류/사유/변경 시각 3개 칼럼을 추가한다.
  기본 분류는 OPEN이다. ORM 쓰기에서 제외해 오래된 entity가 운영 상태를 덮어쓰지 않는다.
  운영 분류 변경은 게시글의 updated_at을 변경하지 않는다.

## 제외 범위와 한계

파싱 정책 자체 변경, 완료된 게시글 재분석, 기존 실패의 일괄 상태 보정, 자동 처리 불가 전환은 제외한다.
장소가 0개인 정상 완료 정책과 게시글 최종 종료 알림 수집/중복 방지 방식은 변경하지 않는다.
기존 작업에 실패 원문·발생 시각이 없다면 상세 사유를 복원할 수 없다. 시각이 없는 이력은 전체 기간에서 확인한다.
원격 DB 변경, 실제 채널 알림 발송, develop/main 병합 및 배포는 이번 구현 단계에서 실행하지 않았다.

## 검증

- 실제 MySQL 8.4: 실패 시각 필터, 최초/관리자 재시도 실패 분리, 수동 상태 변경 후 실패 이력 보존,
  두 재시도 API 차단과 해제, 진행 중 변경 차단, 감사 오류 시 롤백, 동시 상태 변경 직렬화.
- 알림 회귀: 마지막 작업 종료 후 한 건, 동시 수집 중복 방지, 재시도 회차 구분,
  구조화 오류 코드/상세/횟수/관리자 재시도 여부와 비밀값 가림.
- 로컬 모의 API와 인앱 브라우저: 목록→상세→1페이지 복귀, 기간/검색/빈 상태,
  처리 불가 변경/충돌 시 사유 보존/해제, 재시도 대기→재시도 실패 자동 갱신,
  정책 조건 묶음, 기존 파이프라인 조회의 새 상세 연결.
- 1280px 데스크톱과 390px 모바일에서 상세 레이아웃 확인. 390px에서 가로 넘침 없음.
  모의 서버 기반 화면 검증이며 실제 dev/live 데이터 변경 검증과 구분한다.
- 최종 전체 검사 결과는 아래에 기록한다. 동기화 폴더의 생성물 지연을 피하려고 임시 Gradle init으로

## 적용 순서와 롤백

검토 후 dev/live 각각 DDL을 먼저 적용하고 API/worker, 관리자 웹, 알림 전달기를 배포한다.
전달기만 먼저 배포하면 이전 이벤트의 선택 필드가 없어도 기존 요약을 표시한다.
코드 롤백 시 추가 칼럼은 유지할 수 있다. 칼럼 삭제가 필요하면 이전 코드로 복원한 뒤
`ddl/rollback.sql`을 사용한다. 칼럼 삭제는 현재 운영 분류·사유·변경 시각을 지우며 작업 실패 이력은 유지한다.
