# NOOK-348 파싱 실행 안전성과 실패 복구

## 목적과 범위

워커의 처리 시간이 길어져 다른 워커가 작업을 재선점하더라도 이전 실행 결과가 저장되지 않게 한다.
운영자는 실패한 후속 작업을 찾아 해당 단계만 재시도할 수 있다.

- NOOK-349: 실행 직전 단건 선점, 시도 번호를 통한 결과 저장 보호, 실행 가능한 작업 우선 조회.
- NOOK-350: 실패 작업 조회 및 단계 재시도, 사유와 운영자 감사 기록, 관리자 화면.
- NOOK-351: 오류별 재시도 정책. 전체 재분석 회차 격리 및 수동 교정 보존은 별도 구현 대기.

## 성공 기준

1. MySQL에서 동시에 선점해도 활성 작업의 소유자는 하나다.
2. 재선점 이전 실행은 결과 저장·완료·재시도·실패 상태를 변경하지 못한다.
3. 결과 저장 콜백 실패 시 DB 변경이 롤백된다. 외부 서비스 호출은 이 트랜잭션 밖에 둔다.
4. 조회 제한 앞에 실행 중인 작업이 있어도 실행 가능한 대기 작업을 가져온다.
5. 관리자 중복 재시도는 충돌 오류로 거절하며 감사 기록 실패 시 예약도 롤백된다.
6. 관리자 요청은 기존 API에 영향을 주지 않는 새 endpoint로 제공한다.

## 검증

- MySQL 8.4 Testcontainers: 동시 선점, 만료 실행 차단, 결과 롤백, 조회 제한, 중복 재시도, 감사 실패 롤백.
- application: 단건 선점 순서, 만료 실행 무시, 재시도 예산 초기화, 영구 오류 종료, 요청 제한 대기.
- 최종 검증 통과: 전체 테스트 753개, 실패/건너뜀 0개. Detekt 및 모듈 의존 방향 검사 통과.
- 최종 명령: `./gradlew check --no-parallel -Dorg.gradle.jvmargs=-Xmx2g`, `pnpm --dir nook-admin-web build`.
- 사용자 요청에 따라 Chrome 대신 내장 브라우저로 검증했다. 로컬 모의 API로 사유 미입력 제출 차단, 실패 응답 시 사유 보존, 성공 안내/목록 갱신, 상태 필터와 빈 상태를 확인했다. 좁은 화면에서 복구 카드의 과도한 줄바꿈을 수정하고 재확인했다. 지연 응답 중 입력·취소·예약 버튼 비활성화와 다음 페이지/처음으로 복귀도 확인했다. 실제 서버와 연결한 브라우저 통합 검증은 미실행이다.

## 배포 및 제외 범위

NOOK-350의 DDL 적용 절차를 선행한다. dev DDL 적용 완료, develop 자동 배포 진행. live 미적용.
전체 재분석에서 기존 자동 장소 연결을 교체할지 누적할지 사용자 결정 대기 중이다.
따라서 전체 재분석 endpoint, 회차 전환 및 이전 회차 취소, 추가적인 수동 수정 보호는 아직 제공하지 않는다.
