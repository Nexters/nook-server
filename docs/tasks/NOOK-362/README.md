# NOOK-362 직접 추가 검색의 기존 장소 및 연결 게시물 조회

## 목적

직접 장소 검색 결과가 서버에 이미 저장된 장소와 일치하는지 클라이언트가 식별하고, 현재 사용자에게
조회 권한이 있는 연결 게시물을 첫 6개부터 페이지 단위로 확인할 수 있게 한다.

## 범위

- `GET /api/v1/places/search` 각 항목에 nullable `existingPlaceId` 추가
- `(provider, externalPlaceId)`가 정확히 일치하는 기존 장소 식별자 반환
- `GET /api/v1/places/{placeId}/posts?page=0&size=6` 추가
- 첫 페이지 기본 크기 6, page/size 기반 pagination 제공
- 기존 장소 상세 조회와 동일한 인증 및 소유 데이터 가시성 재사용
- OpenAPI, HTTP Client 예시와 계층별 테스트

## API 계약

### 직접 연결 장소 검색

기존 응답 필드를 유지하고 각 검색 항목에 다음 필드를 추가한다.

```json
{
  "selectionToken": "...",
  "existingPlaceId": 17
}
```

- 동일 provider의 외부 장소 ID가 서버에 있으면 내부 식별자를 반환한다.
- 아직 저장되지 않은 장소면 `null`을 반환한다.
- 기존 클라이언트는 추가 필드를 무시할 수 있다.

### 연결 게시물 목록

```http
GET /api/v1/places/17/posts?page=0&size=6
Authorization: Bearer {accessToken}
```

- 응답은 기존 장소 상세의 `posts`와 같은 페이지 형식이다.
- `size`를 생략하면 최초 6개를 반환한다.
- 다음 페이지는 `page`를 증가시켜 조회한다.

## 가시성 결정

현재 장소 상세는 로그인 사용자가 직접 저장한 게시물만 조회하고, 본인의 북마크나 연결 게시물이 없는
장소는 `PLACE_NOT_FOUND`로 처리한다. 다른 사용자의 저장 게시물을 일반 공개 데이터로 간주하는 정책은
기존 계약에 없다. 따라서 이번 작업은 같은 조회 포트를 재사용하며 다른 사용자의 게시물을 새로 공개하지
않는다. 다른 사용자의 게시물 노출은 공개 범위, 삭제·비공개 상태, 공유 아카이브 정책을 별도 확정한 뒤
후속 작업으로 진행해야 한다.

## 제외 범위

- 다른 사용자의 비공개 저장 게시물 노출
- 공유 링크 없이 공유 아카이브 게시물 노출
- 검색 결과에서 게시물 본문을 함께 반환
- 데이터베이스 스키마 변경

## 성공 기준

- 저장된 provider 장소와 검색 후보가 정확한 외부 ID로 매칭된다.
- 미저장 후보의 `existingPlaceId`는 `null`이다.
- 권한이 있는 기존 장소의 연결 게시물을 기본 6개부터 페이지 조회할 수 있다.
- 기존 장소 상세와 동일하게 현재 사용자의 저장 게시물만 반환한다.
- 기존 검색과 장소 상세 계약이 유지된다.
