# NOOK-400 온보딩 Instagram CTA 이후 첫 저장 전환

## 목적

온보딩 Instagram CTA 클릭과 이후 보관함 저장 성공의 시간적 연관성을 측정한다.
대표 지표는 클릭 후 10분 이내 첫 저장률이며 5분/30분, 24시간 분포를 함께 제공한다.
온보딩의 인과 효과나 Instagram 내부 행동을 측정한 것으로 해석하지 않는다.

## 범위

- 인증된 클라이언트의 CTA/Share Extension 이벤트 수집 API와 멱등 저장
- 기존 서버 `POST_SAVE` 이벤트를 이용한 전환 집계 및 어드민 온보딩 화면
- DDL, API `.http`, 클라이언트 전달 계약, 경계/인증/DB 쿼리 테스트
- Share Extension은 서버 수집·집계를 준비한다. 실제 iOS 수집 가능 여부는 클라이언트 확인 대기다.

## 제외 범위

- iOS 코드 수정/배포, 실제 Share Extension 실행 확인, Instagram 내부 조회·공유 버튼 추적
- 과거 CTA 데이터 복원, 기존 POST_SAVE 저장 실패 보장 수준 변경, 전환 인과 추론
- 운영 DB DDL 적용 및 서비스 배포

## 확정 집계 기준

- 사용자별 전체 수집 이력의 최초 `INSTAGRAM_CTA_CLICK`을 기준점으로 사용한다.
  반복 클릭으로 기준을 초기화하지 않으며, 해당 최초 클릭일이 선택 기간(KST, 양끝 포함)에 들어와야 한다.
- 조회 기간은 최대 90일. 후속 관측은 조회 시각까지, 클릭 이후 최대 24시간이다.
  기간 마지막 날 클릭 후 다음 날 저장도 관측한다.
- 첫 저장은 가입 후 최초가 아니라 CTA 이후 최초 `POST_SAVE`다. 정확히 클릭/5분/10분/30분/24시간인 이벤트도 포함한다.
- 저장은 보관함 저장 성공이며 콘텐츠/장소 파싱 완료와 다르다. 이미 저장된 게시물 재요청은 기존 로직이 이벤트를 만들지 않는다.
- 5/10/30분 잠정률: 시간 내 저장한 사용자 / 전체 CTA 사용자.
- 관측 완료율: 해당 시간이 지난 사용자 중 시간 내 저장한 사용자 / 해당 시간이 지난 사용자.
  분모 0이면 비율은 null이며 UI에서는 `—`로 표시한다.
- 24시간 분포: 24시간이 지난 사용자만 대상. 서로 다른 post ID를 세어 0/1/2/3+로 나눈다.
  삭제 후 같은 게시물 재저장은 중복 제외. 아직 24시간이 안 지난 사용자는 별도 관측 중 인원으로 표시한다.
- 중앙값: 24시간 관측 완료 집단에서 24시간 안에 전환한 사용자의 첫 저장 소요 시간(초).
  전환자가 없으면 null이며 짝수 표본은 가운데 두 값 평균이다.
- Extension: 24시간 관측 완료 집단만 대상으로 CTA 이후 첫 진입을 선택한다.
  이후 저장은 첫 진입 이상, CTA+24시간 이하의 최초 저장이다.
  진입률 분모는 24시간 완료 CTA 사용자, 저장률 분모는 진입 사용자다.
  진입 데이터가 없으면 퍼널은 null이며 실제 미진입과 미수집을 구별할 수 없다고 표시한다.
- 늦게 도착한 더 이른 CTA는 최초 클릭과 집계 기간을 바꿀 수 있다. 관측 완료는 시간 경과를 뜻하며 데이터 불변을 보장하지 않는다.

## 구현

기존 `analytics_events`는 저장 전환의 근거로 읽기만 한다. 온보딩 이벤트는 `onboarding_events`에 저장해
기존 활성/재방문/행동 분포의 의미를 유지한다. `created_at`이 서버 최초 수신 시각,
`occurred_at`이 클라이언트 실제 발생 시각이다. `(member_id, event_id)` 유니크 키로 재시도를 제거한다.
동일 ID의 종류나 시각을 바꾸어 보내면 400이다. DB 오류를 삼키지 않아 5xx 응답 후 재시도할 수 있다.
회원별 조회는 500명 단위로 저장/진입 기록을 조회하며, 사용자별 24시간 경계는 집계 계층에서 다시 제한한다.

## API

- `POST /api/v1/onboarding/events`: 인증 필요, `eventId` UUID, `eventName`, `occurredAt` UTC.
  성공/동일 이벤트 재전송 204(본문 없음), 잘못된 요청 400, 인증 오류 401, 저장 장애 5xx.
  종류는 `INSTAGRAM_CTA_CLICK`, `SHARE_EXTENSION_OPEN`만 허용한다.
  발생 시각은 서버 현재 시각 이하 및 과거 7일 이내. DB 정밀도에 맞춰 마이크로초로 절삭한다.
- `GET /api/admin/v1/onboarding-conversion?from=YYYY-MM-DD&to=YYYY-MM-DD`: 기존 어드민 인증 사용.
  `ApiResponse` envelope의 `success`에 사용자 수/기간별 분자·분모·비율/중앙값/분포/Extension을 반환한다.

클라이언트 전달 문안과 연동 확인 항목은 [client-handoff.md](client-handoff.md)를 참조한다.

## DDL과 배포 순서

1. staging에서 `ddl/up.sql` 적용·검증 후 서버/어드민 배포.
2. 클라이언트 CTA 수집 배포. 두 번째 단계까지는 실제 전환 데이터를 기대할 수 없다.
3. 동일 테스트 계정으로 CTA → 보관함 저장 → 어드민 집계를 확인한다.
4. Share Extension 가능 여부 및 인증/오프라인 재시도를 클라이언트와 확인하고 지원 시 활성화한다.
5. live DDL/배포는 별도 승인된 절차에서 진행한다.

신규 테이블 생성이며 기존 데이터 변경은 없다. FK는 생성하지 않는다.
DDL은 반복 실행 가능하나 기존에 다른 스키마의 동명 테이블이 있으면 자동 교정하지 않는다.
롤백은 애플리케이션 롤백 후 `ddl/rollback.sql`을 적용하며, 해당 테이블 데이터가 유실되므로 사전 백업이 필요하다.

- 적용/검증 시각: 2026-10-07 23:27:52 KST (14:27:52 UTC).
- 대상: live `nook` DB, MySQL 8.4.8.
- 승인: 백도현. 실행: Codex, 라이브 관리자 계정 `nook_admin` 사용.
- staging 접속 정보가 없어 사전 검증을 생략하고 live에 직접 적용하는 예외를 사용자가 승인했다.
  실제 MySQL 8.4의 테스트용 DB에서 DDL/rollback 검증은 완료한 상태였다.
- 적용 파일: `ddl/up.sql` (SHA-256 `092b77676ae82698a1cebad09e1ea0340b261b0de1669ba28917eecdf34f7868`).
- 적용 전 테이블 부재 확인 후 신규 생성. 적용 후 8개 칼럼의 타입/제약/COMMENT,
  PK 및 명시된 유니크·조회 인덱스, FK 0개, 행 수 0개를 확인했다.
- 서버 및 어드민 배포는 별도이며 이 DDL 작업에서 실행하지 않았다.

- CTA 원래 시각과 인증 사용자 유지, 중복 전송 1건, 장애 시 성공 응답 금지

- 미관측 사용자 분리, 0분모/빈 상태, 홀수·짝수 중앙값 및 순서가 맞는 Extension 퍼널 검증
