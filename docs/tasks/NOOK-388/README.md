# 영문 주소를 이용한 장소 검색·매칭 개선

## 목적

영문 업체명·주소로 한글 장소 후보를 찾아도 최종 근거 검증에서 제외되던 조건을 개선한다.
처음에는 기술 확인 범위였으나, 사용자가 같은 이슈에서 구현까지 진행하도록 범위를 확장하고
원문 보존, 기존 OpenAI 호출 활용, 검색 우선순위와 최종 검증 보완 계획을 승인했다.

## 범위

- 기존 장소 추론 응답에 선택값 `normalizedAddressHint`를 추가한다. `addressHint`는 원문을 유지한다.
- OpenAI에 확실한 국내 영문 주소의 한글 변환과 영문 상호의 한글 검색 표기를 요청한다.
- 상호명 언어로 최대 네 개를 검색하고 장소를 확정하지 못하면 반대 언어로 최대 세 개를 검색한다.
- 최종 후보에 상호 일치, 정확한 도로명·건물 번호, 지역과 층·호 호환성, 검색 근거를 요구한다.
- 단서 병합과 이미지 카드의 주소 복원에서 원문 주소와 변환 주소의 연결을 유지한다.

## 제외 범위

추가 OpenAI 호출, 해외 주소 지원, 모든 로마자 표기의 결정적 번역, provider 정책 변경,
공개 endpoint/request 변경, DDL, 과거 게시물의 일괄 재처리 및 무관한 파싱 알림 오류 수정은 제외한다.

## 구현과 성공 기준

`5 Gyedong-gil, Jongno-gu, Seoul`처럼 국내 도로명·지번의 `-ro`, `-gil`, `-dong`,
`-eup`, `-myeon`, `-ri`와 건물 번호가 식별되는 입력에 한글 변환 주소를 사용한다.
번호가 원문과 다르거나 층·호를 변경·생략한 변환은 매칭에 사용하지 않고 해당 후보를 거절한다.
Seoul 등 광역 도시 표기는 변환 도시와 비교하고, 한글 변환 주소와 후보 사이의 시·구·군 충돌을 거절한다.
변환 주소가 없거나 지원 형태가 아닌 입력은 기존 정책을 유지한다.

변환 주소만 같다는 이유로 같은 건물의 다른 가게를 확정하지 않는다. 원문 이름 또는 추론 검색어의
상호 표기가 후보 이름과 일치해야 하며, 후보는 해당 한글 주소나 상호 검색으로 실제 반환돼야 한다.
이미지 단서는 영문 주소 원문이 이미지 evidence에 있어야 변환 주소를 근거로 사용할 수 있다.
후보 선택 모델이 잘못된 후보를 고르더라도 최종 검증을 우회하지 않는다.

성공 기준은 한글 상호+영문 주소 및 한글 검색 별칭이 있는 영문 상호+영문 주소의 처리 완료,
건물 번호·도로명·지역·층·호 충돌과 같은 주소의 다른 상호 거절, 기존 한글 처리 및 저장 단서 읽기 유지다.
`normalizedAddressHint`는 기본값 null인 내부 단서 필드이며 기존 저장 JSON도 읽을 수 있다.
추론은 한 번에 두 언어의 검색어를 최대 일곱 개까지 반환한다. 트랜잭션 경계와 공개 API 계약은 유지한다.

## 언어별 4+3 검색 정책

사용자가 승인한 최종 정책은 한글 상호에 한글 네 개→영문 세 개, 영문 상호에 영문 네 개→한글 세 개다.
상호명과 검색어에 한글이 포함되면 한글로 분류한다. 한글 상호+영문 주소는 한글 이름·검색어를
먼저 사용하고 영문 주소는 영문 단계에 둔다. 영문 상호의 한글 변환 주소는 한글 단계에 둔다.
중복 검색어를 제거하며 확실한 검색어가 부족하면 수를 채우려고 추측하지 않는다.
네 개·세 개는 검색어 수의 상한이며 provider 호출 횟수나 반환 후보 수가 아니다.

1차 검색 결과가 있어도 모델이 선택하지 못하거나 최종 검증에서 탈락하면 2차로 넘어간다.
검증을 통과한 strict 후보가 검색 중 나오면 해당 단계의 남은 검색을 중단하며, 1차에서 장소가
확정되면 2차는 실행하지 않는다. 두 단계의 후보는 각 단계에서 독립적으로 판정한다.
검색 provider 오류는 언어 fallback으로 감추지 않고 기존 재시도 정책으로 전달한다.
반대 언어 검색어가 없으면 기존 실패를 유지하고, 2차도 실패하면 2차의 구체적인 실패를 반환한다.
추론 API 추가 호출은 없으며, 1차 모델 후보 선택이 실패한 뒤 2차도 모델 선택이 필요한 경우에는
후보 선택 API가 최대 두 번 호출될 수 있다.

## 실제 외부 호출 검증

2026-10-11 KST에 변경된 adapter의 요청을 캡처해 합성 텍스트 세 건과 후보 선택 두 건으로
실제 OpenAI API를 호출했다. 인증 정보는 기록하지 않았고 애플리케이션 DB 쓰기는 없다.
[inference-results.json](verification/inference-results.json)과 [provider-results.json](verification/provider-results.json)은
구현 전 조사 기록이며, [implementation-results.json](verification/implementation-results.json)은 구현 후 결과다.

- 영문 주소가 있는 두 입력 모두 `서울특별시 종로구 계동길 5`를 반환하고 영문 원문을 유지했다.
- 영문 상호·주소 입력에는 `카페 어니언 안국 종로구 계동길 5` 등의 한글 검색어도 반환했다.
- 이 실제 검색어 세 개로 Naver/Kakao 총 여섯 번 조회한 결과 모두 HTTP 200이었다.
  Kakao는 변환 주소 검색에서 ‘어니언 안국’을 첫 후보로 반환했고, Naver도 한글 상호 검색어로 반환했다.
  [implementation-provider-results.json](verification/implementation-provider-results.json)에 기록했다.
- 후보 선택 모델은 같은 주소의 ‘다른 가게’도 선택했다. 그래서 모델 선택 또는 주소 일치만으로
  통과시키는 방식을 채택하지 않고, 서버의 상호 일치 및 주소 검증으로 거절하도록 구현했다.

위 외부 호출 기록은 영문 주소 정규화 구현 시점의 요청이며, 이후 확장한 4+3 검색 정책은
단위 테스트와 처리 흐름 테스트로 검증했다. 위 결과는 특정 표본과 시점의 관찰이다.
전체 Instagram 게시물·OCR·운영 DB 저장까지 이어지는
실환경 처리나 모든 영문 주소의 성공률을 검증한 것은 아니다. 한글 변환과 별칭 생성은 모델에
의존하며, 별칭이 없거나 변환이 불확실한 경우에는 기존 정책으로 실패할 수 있다.
이미 추론해 저장한 단서는 자동으로 재추론하지 않는다.

## 코드 검증

- 조사 테스트 10개, 영문 주소 매칭 테스트 10개, 언어 검색 테스트 8개,
  처리 흐름 테스트 4개, adapter/이전 JSON 읽기 테스트 2개 추가.
- 기존 저장 테스트의 JSON 기대값에 새 선택 필드의 null을 반영했다.
- 전체 Detekt 및 모듈 의존 방향 검사, `git diff --check` 통과.
- 최종 `./gradlew check --continue --max-workers=2 -Dorg.gradle.jvmargs='-Xmx2g -XX:MaxMetaspaceSize=768m'`
  실행: 전체 테스트 878개 중 877개 통과, 기존 `ParsingSummaryMySqlTest` 1개 실패.
  `legacy fingerprint migrates without republishing an existing failure` 146행의 실패이며,
  NOOK-382에서 변경 없는 main에서도 같은 실패를 확인했다. 이후 main에서 해당 테스트의 변경이 없고
  이번 작업도 관련 운영 코드와 테스트를 수정하지 않았다. 전체 check는 통과하지 못했다.
- 검증일: 2026-10-11 KST.
- 추가 테스트 34개와 기존 장소 처리·주소·adapter·저장 테스트는 통과했다.

## 배포 및 롤백

DDL은 없다. API와 장소 처리 워커에 동일한 코드 버전을 배포한다.
새 필드를 쓰는 API보다 해당 필드를 읽는 워커를 먼저 배포한다. 이전 저장 단서에는 기본값 null이 적용된다.
롤백 시 먼저 API 쓰기를 이전 버전으로 돌리고, 새 필드가 포함된 대기 작업의 이전 워커 읽기 호환성을
확인한 후 워커를 되돌린다. 데이터 변경이나 과거 작업 재처리는 별도로 실행하지 않았다.
develop 병합·푸시와 main 대상 PR 등록은 최종 변경·검증 결과의 사용자 리뷰 후 진행한다.
