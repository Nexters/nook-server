# NOOK-410 저장 실패 게시물 복구와 관리자 단계별 재시도

이슈: https://linear.app/nooknook/issue/NOOK-410

## 목적과 범위

앱에서 기존 실패 저장 건의 식별자만으로 복구를 요청한다. URL과 사용자·아카이브 연결은 최초 저장 시
이미 영속화되어 있으므로 새 게시물이나 아카이브 연결을 만들지 않고 콘텐츠 수집 작업만 재개한다.
관리자는 게시물별 본문 수집·장소 인식 실패를 각각 선택해 재시도할 수 있다.

- 사용자 복구 요청 및 처리 상태 조회 API 추가.
- 본인 소유의 활성 저장 게시물만 허용. 다른 사용자/삭제 건은 POST_NOT_FOUND.
- 실패 콘텐츠 작업만 PENDING으로 전환하며 진행 중/완료 건에는 새 실행을 만들지 않음.
- 원본 콘텐츠 작업 행 잠금으로 같은 원본에 대한 요청을 직렬화함.
- 총 실행 횟수는 유지하여 이전 실행 결과의 저장을 차단하고 현재 회차 retryAttemptCount만 초기화.
- 실패 이유와 시각은 유지. 재실패하면 기존 worker 정책에 따라 FAILED가 되고 이후 재요청 가능.
- 관리자가 처리 종료한 게시물은 기존 processing disposition 정책에 따라 복구를 거절.
- 활성 아카이브가 모두 삭제됐으면 GROUP_NOT_FOUND로 중단. 일부만 남으면 기존 활성 연결만 유지.
- 앱 종료와 무관하게 기존 durable worker dispatcher가 PENDING 작업을 처리.
- 콘텐츠 복구 이후 기존 장소 처리와 완료 푸시 흐름을 재사용. 장소 인식 실패도 게시물 저장 완료로 취급.
- 아카이브가 처리 도중 삭제돼도 해당 연결을 다시 생성하지 않음. 원본 수집 작업은 다른 저장 사용자와 공유될 수 있음.

## 관리자 재시도

기존 `POST /api/admin/v1/parsing-posts/{postId}/retry` 요청에 선택값 `jobType`을 추가한다.

| 선택 | 동작 |
| --- | --- |
| 생략 | 기존처럼 실패한 모든 단계 재시도 |
| POST_CONTENT | 실패한 본문 수집만 재시도 |
| PLACE_PARSING | 실패한 장소 인식만 재시도; 본문 수집 완료 필수 |

미선택 단계·완료 단계는 유지한다. PENDING/PROCESSING 상태의 중복 요청은 기존 409 정책을 따른다.
처리자·사유·선택한 실패 작업은 기존 감사 로그에 기록한다. 관리자 화면의 각 실패 단계에서 선택 가능하다.

장소 이미지(PLACE_THUMBNAILS), 게시물 미디어(POST_MEDIA), 장소 태그(PLACE_TAGS)는 기존
`POST /api/admin/v1/parsing-jobs/{jobId}/retry`로 한 작업씩 재시도할 수 있다.
한 이미지 작업에 포함된 장소들의 목록은 기존 작업 payload 범위를 따른다.
이미지 결과가 비어 장소 상태가 FAILED여도 후속 작업 자체는 COMPLETED일 수 있다.
그 경우에는 기존 장소 상세의 **사진·태그 재처리**를 사용한다. 이 경로는 수동 교정값을 보존하며
장소 하나만 다시 수집하고 결과를 UPDATED/PRESERVED/NO_DATA 등으로 구분한다.

이 장소 재처리 요청에도 선택값 `target`을 추가했다. `ALL`(기본)은 기존 사진·태그 모두,
`PHOTOS`는 사진만, `TAGS`는 태그만 처리한다. 선택하지 않은 항목은 provider 호출과 결과 변경을 모두
생략하고 기존 값을 유지한다. 관리자 장소 상세의 다이얼로그에서도 선택할 수 있다.
선택은 기존 항목별 작업 상태(PENDING/PRESERVED)에 영속화하므로 DDL은 필요하지 않다.
선택 항목은 감사 로그에 남긴다. API와 worker 변경을 함께 배포해야 한다.

## 제외 범위

- 앱 UI/버튼/푸시 진입 화면 구현: 앱 저장소에서 아래 연동 명세에 따라 연결 필요.
- 정상 게시물의 사용자 장소 재인식, 새 아카이브 선택, URL 재입력.
- 완료된 본문·장소 인식의 강제 재수집 및 기존 관리자 기능의 중복 구현.
- DB/DDL 변경, 운영 실패 작업 실제 재실행, provider 실호출, 배포.

## 성공 기준과 검증

- 입력 없이 기존 저장 건 복구, 다른 사용자 접근 차단, 삭제된 아카이브 중단.
- 중복 요청 시 재실행하지 않고 현재 상태 반환, 재실패 이후 재요청.
- 총 실행 횟수·실패 이력·기존 저장 연결 보존.
- 관리자 단일 단계 재시도에서 미선택 작업 보존, 선행 작업·실행 중 상태 검증.
- 기존 완료 푸시와 장소 없는 저장 동작의 회귀 검증.
- 단위·H2 테스트, Detekt, 모듈 의존 검사, 관리자 TypeScript/Vite build.
- Docker/MySQL 컨테이너 테스트는 임시 외부 init script로 제외. 브라우저 동작 검증은 직접 수행하지 않음.

## 검증 결과

- 단위·H2 테스트 869개 통과(실패/오류/skip 0). MySQL 컨테이너 테스트는 실행 필터로 제외.
- Detekt 및 모듈 의존 검사 통과.
- 관리자 `pnpm build`(TypeScript 및 Vite) 통과. 기존 번들 크기 경고는 남아 있음.
- 사용자 복구의 소유권·삭제 아카이브·중복 요청·재실패 후 재요청·총 시도 횟수 보존 검증.
- 관리자 본문/장소 단일 단계 선택과 전체 재시도 호환성, 선행 콘텐츠 미완료 차단 검증.
- 사진만/태그만 요청 전달, 미선택 provider 호출 생략, 작업 선택의 enqueue→claim 유지,
  미선택 값 및 수동 수정값 보존 검증.
- 기존 worker의 장소 인식 실패 시 완료 푸시 테스트도 포함해 통과.
- `git diff --check` 통과. 공개 API의 기존 계약은 유지하며 선택 필드/새 endpoint만 추가.

```bash
JAVA_HOME=$(/usr/libexec/java_home -v 25) ./gradlew check --init-script /tmp/nook-410-unit-h2.gradle --no-daemon --max-workers=2
cd nook-admin-web && pnpm build
```

임시 init script는 모든 Test task에서 `**/*MySqlTest*`를 제외한다. 저장소 테스트 설정은 변경하지 않았다.
브라우저/실제 MySQL 동시성/provider 실호출/실제 푸시 전달은 미검증이며 배포 후 사용자 확인이 필요하다.
자세한 절차는 `client-handoff.md`를 따른다.
