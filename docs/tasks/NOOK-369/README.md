# NOOK-369 게시물 단위 공유 및 내 아카이브 저장

이슈: https://linear.app/nooknook/issue/NOOK-369

## 목적과 확정 정책

2026-10-18 사용자가 다음 두 정책을 확정했다.

- 공유 시점의 공개 콘텐츠·장소 목록·표시 순서를 스냅샷으로 유지한다.
- 이미 같은 원본을 저장한 사람은 기존 메모·장소 연결을 유지하고 선택한 아카이브 연결만 추가한다.

게시물 하나만 공개하는 전용 링크를 추가한다. 기존 아카이브 공유는 원본 참조 정책을 유지한다.
공유자의 개인 메모, 아카이브 목록, 장소 메모, 북마크 여부는 새 공개 응답에 포함하지 않는다.

## 현재 문제와 변경

- 기존 저장 API는 아카이브 공유 토큰을 검증하며 게시물 단독 공유 링크가 없었다.
- 기존 `SharedPostSavePersistenceAdapter`는 공유자의 사용자별 장소 연결 대신 공통 원본 장소를
  복사해 삭제한 장소가 되살아나거나 직접 추가한 장소가 누락될 수 있었다. 사용자별 연결을 복사하도록 수정했다.
  기존 아카이브 공유로 아직 처리 중인 게시물을 저장하는 동작은 유지하며, 이 경우 최초 worker의 장소 채움을 막지 않는다.
- 새 전용 링크는 32바이트 SecureRandom 토큰을 사용한다. DB에는 SHA-256만 저장하며 원문을 저장하지 않는다.
- 발급 시 공유자의 저장 행을 잠그고 완료된 게시물의 공개 콘텐츠와 장소 목록을 JSON으로 고정한다.
  장소 인식 실패나 장소가 없는 게시물도 콘텐츠 저장이 완료됐다면 공유할 수 있다.
- 저장은 본인 소유의 활성 아카이브만 허용한다. 아카이브·공통 게시물·저장 행을 잠그고 저장 건과
  장소·아카이브 연결을 짧은 트랜잭션에서 처리한다. 공통 게시물 잠금은 기존 일반 저장의 잠금과 같다.
  중복 요청이 대기 후 재개돼도 이전 저장의 아카이브 연결을 볼 수 있도록 현재 읽기(행 잠금)를 사용하고,
  삭제했던 장소 연결의 초기화는 과거 읽기 스냅샷에 의존하지 않는 bulk DELETE로 처리한다.
- 새로운 수신자의 저장 건은 스냅샷 장소만 복사한다. 기존 활성 저장 건은 메모·장소를 덮어쓰지 않는다.
  삭제했던 수신자 저장 건을 복구하면 이전 장소 연결을 스냅샷으로 다시 초기화한다.
- 선택한 아카이브의 기존 구독자 지도 반영도 기존 공유 북마크 동기화 기능을 사용한다.

## 독립성의 데이터 경계

Instagram 콘텐츠의 공통 원본 `posts`와 공용 장소 카탈로그 `places`는 기존처럼 재사용한다.
사용자별 `user_saved_posts`, `user_saved_post_places`, 아카이브 연결과 개인 메모를 독립적으로 관리한다.
공유자의 이후 장소 추가·삭제, 저장 건 삭제는 수신자 연결에 전파하지 않는다.
공용 카탈로그에 대한 관리자의 정보 교정까지 장소 행을 통째로 복제해 분리하는 기능은 범위 밖이다.

공유 복사본에는 `place_links_frozen`을 기록한다. 이후 공통 장소 파싱이 다시 실행되어도 장소를
자동으로 추가하지 않으며, 원본의 재처리/실패 때문에 완료된 복사본이 처리 중/실패 화면으로 바뀌지 않는다.
수신자의 직접 장소 추가·삭제는 계속 허용하고, 복사본의 복구 API 호출로 공통 수집을 재시작하지 않는다.
빈 장소 목록도 정상적인 독립 스냅샷으로 취급한다.

원본 삭제 시 `share_generation`을 새 UUID로 바꾼다. 링크에 저장한 세대와 다르면 410을 반환한다.
게시물 직접 삭제와 마지막 소속 아카이브 삭제 모두 기존 `softDelete`를 통해 이 규칙을 적용한다.
원본 재저장/복구로 세대를 되돌리지 않으므로 예전 링크는 다시 활성화되지 않는다.
`@DynamicUpdate`는 늦게 저장되는 메모 수정이 삭제 세대나 복사본 고정 상태를 이전 값으로 덮어쓰지 않게 한다.
이미 저장한 수신자는 자기 저장 ID로 계속 조회·편집할 수 있다.

## API

| API | 인증 | 동작 |
| --- | --- | --- |
| POST /api/v1/posts/{postId}/share-links | 필수 | 내 사용자 저장 ID의 현재 스냅샷을 새 토큰으로 발급 |
| GET /api/public/v1/post-shares/{token} | 선택 | 고정 공개 콘텐츠와 로그인 사용자의 viewerSavedPostId 조회 |
| POST /api/v1/post-shares/{token}/save | 필수 | groupIds의 본인 아카이브에 저장; postId와 alreadySaved 반환 |

기존 아카이브 공유·조회·저장 endpoint와 request/response 계약은 유지한다.
프론트는 반환한 token으로 앱/웹 공유 랜딩 URL을 구성하며, API 서버가 앱 호스트나 UI 라우트를 정하지 않는다.
자세한 필드·오류·CTA·검증 절차는 `client-handoff.md`와 controller별 `.http` 파일을 따른다.

## DDL과 반영

- `ddl/up.sql`: `post_share_links` 신규 생성, `user_saved_posts`에 `share_generation`, `place_links_frozen` 추가.
- 기존 저장 건은 초기 세대 빈 문자열과 frozen=false를 유지한다. 기존 공유 복사본의 출처를 추측해 backfill하지 않는다.
- 테이블/칼럼 COMMENT, 유니크/조회 인덱스를 명시하며 물리 FK는 없다. 적용은 반복 실행 가능하도록 작성했다.
- `ddl/rollback.sql`: 새 테이블과 두 칼럼을 제거한다. API/worker를 이전 버전으로 되돌린 뒤에만 실행한다.
  공유 링크 이력과 독립성 보호 플래그가 사라지므로 백업과 영향을 검토해야 한다. 사용자 장소 연결은 삭제하지 않는다.
- API와 worker 모두 새 칼럼을 사용한다. DDL 선적용 후 API/worker를 함께 반영해야 한다.
- 개발 DDL은 아래 기록대로 적용했다. 운영 DDL, 외부 provider 호출은 하지 않았다.
