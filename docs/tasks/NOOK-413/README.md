# NOOK-413 Instagram 빈 콘텐츠 성공 처리 방지

이슈: https://linear.app/nooknook/issue/NOOK-413

## 목적과 관찰 가능한 성공 기준

`DeUL9gVEtup`에서 Apify 콘텐츠 없음 → Bright Data 폴백은 정상 동작했지만,
Bright Data 응답에 본문·실제 미디어 URL이 없어도 서버가 완료 상태로 저장했다.
개발 postId=428, 운영 postId=1968은 기본 제목·장소 0개로 완료됐고 빈 응답이 provider 캐시에 남았다.

- 본문이 null/공백이고 매핑된 미디어도 없는 응답은 `POST_CONTENT_PROVIDER_ERROR`로 처리한다.
- 실패 결과는 기존 재시도 정책을 따르고, 재시도 소진 시 실패로 종료한다. 완료 저장·완료 알림 경로에 진입하지 않는다.
- Apify의 빈 결과는 Bright Data 폴백 대상이다. 양쪽이 모두 빈 콘텐츠면 성공으로 종료하지 않는다.
- 빈 응답은 캐시하지 않는다. 기존의 빈/손상된 캐시는 무시·제거한 뒤 재수집하고 정상 응답만 저장한다.
- 본문만 있는 게시물, 미디어만 있는 게시물, 실제로 장소가 없는 정상 게시물은 계속 허용한다.

## 구현 범위

- 두 provider extractor의 매핑 결과에 공통 콘텐츠 검증을 적용했다.
  작성자·게시물 ID·타임스탬프·장소 태그만 존재하는 것은 실제 콘텐츠로 취급하지 않는다.
  미디어의 유효 여부는 기존 mapper가 URL이 없는 항목을 제외한 결과를 사용한다.
- 캐시 응답도 같은 parser/검증을 거친다. 기존 provider 파싱·검증 예외면 해당 캐시를 제거하고 실제 수집을 진행한다.
- 캐시는 provider·source·게시물 ID와 읽었던 응답 본문이 일치할 때만 짧은 트랜잭션에서 제거한다.
  다른 요청이 갱신한 응답을 오래된 요청이 제거하지 않는다. 외부 provider 호출은 이 트랜잭션 밖에서 실행한다.
- API 계약·실패 코드·정상 장소 0개 정책은 유지한다. DB 스키마 변경과 DDL은 없다.

## 제외 범위와 반영 후 확인

기존 저장 게시물이나 운영 캐시를 일괄 수정하지 않는다. 이미 완료로 저장된 빈 게시물은 코드 배포만으로
자동 복구되지 않으며, 관리자에서 콘텐츠 재수집을 명시적으로 실행해야 한다.
이 작업에서는 실제 재수집·외부 provider 호출·배포·브라우저 조작을 수행하지 않는다.

반영 후 추가 확인이 필요하면 관리자가 해당 게시물의 콘텐츠 재시도를 실행한다.
다시 빈 응답이면 재시도/최종 실패로 표시되고 완료 알림이 발생하지 않아야 한다.
정상 콘텐츠를 받으면 새 응답으로 캐시되고 기존 콘텐츠·장소 처리 흐름을 진행해야 한다.

## 검증

- 단위: 두 provider의 빈 응답 차단·미캐시, 본문만/미디어만 존재하는 정상 응답,
  빈/손상 캐시 무시 후 재수집·새 캐시 저장, 재수집도 비어 있으면 실패 유지, 실제 extractor 간 폴백.
- 작업 유스케이스: provider 오류와 재시도 소진 시 완료 저장·추론 없이 실패.
- H2: 캐시 조건부 삭제·재저장, 다른 provider 보존, 다른 요청이 갱신한 응답 보존.
- 최종 단위·H2 테스트 903개 통과(실패·오류·skip 0), Detekt·모듈 의존 검사와 `git diff --check` 통과.
- 첫 전체 실행에서 기존 Prometheus HTTP histogram 노출 테스트가 한 차례 실패했다.
  관련 코드·테스트를 변경하지 않고 전체 검증을 다시 실행해 통과했다. 빈 콘텐츠·캐시 회귀 테스트는 모두 통과했다.
- MySQL 컨테이너 테스트는 외부 임시 init script로 제외한다. Docker·브라우저·provider 실호출은 실행하지 않는다.

```bash
JAVA_HOME=$(/usr/libexec/java_home -v 25) ./gradlew check --init-script /tmp/nook-413-unit-h2.gradle --no-daemon --max-workers=2
```
